CÁC BƯỚC THỰC HIỆN TUẦN TỰ
  1. Client gửi yêu cầu đặt sân: Gửi request POST /api/bookings với dữ liệu: customerId, fieldId, bookingDate, startTime, endTime.
  2. Booking Service chặn luồng: Tạm ngưng việc ghi cơ sở dữ liệu để thực hiện cuộc gọi đồng bộ GET /api/fields/{fieldId} sang Field Service.
  3. Field Service truy vấn Catalog DB:
    - Nếu sân tồn tại: trả 200 OK kèm JSON thông tin sân.
    - Nếu không có: trả 404 Not Found.
  4. Phân nhánh xử lý:
    - Hợp lệ (200 OK): Tạo bản ghi Booking, trả về 201 Created cho Client.
    - Không tìm thấy (404): Hủy giao dịch, trả về 404 Error cho Client.
Đặc điểm Đồng bộ: Luồng xử lý của Booking Service phải chờ (blocking) cho đến khi Field Service hoàn thành và trả phản hồi về mạng.

FieldController.java (Provider Service - Port 8081)
@RestController
@RequestMapping("/api/fields")
public class FieldController {
    private final Map<String, FieldResponse> db = new ConcurrentHashMap<>();

    public FieldController() {
        // Dữ liệu mẫu của catalog Anta
        db.put("f-101", new FieldResponse(
            "f-101", "Sân bóng cỏ nhân tạo 7 người - Sân A",
            "FOOTBALL", new BigDecimal("350000"), "AVAILABLE"
        ));
    }

    @GetMapping("/{id}")
    public ResponseEntity<?> getFieldById(@PathVariable String id) {
        FieldResponse field = db.get(id);
        if (field == null) {
            // Trả về 404 Not Found nếu không tìm thấy ID
            return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(Map.of("status", 404, "error", "Sân '" + id + "' không tồn tại"));
        }
        // Trả về 200 OK kèm thông tin JSON
        return ResponseEntity.ok(field);
    }
}

NGHIỆP VỤ & NGUYÊN TẮC CỐT LÕI
  • Tính Idempotent (Bảo toàn trạng thái): Phương thức GET không làm thay đổi trạng thái dữ liệu, an toàn cho việc gọi lại nhiều lần (Retry).

BookingController.java (Consumer - Port 8080)
@RestController
@RequestMapping("/api/bookings")
public class BookingController {
    private final RestClient fieldClient;

    public BookingController(RestClient.Builder builder) {
        this.fieldClient = builder.baseUrl("http://localhost:8081").build();
    }

    @PostMapping
    public ResponseEntity<?> createBooking(@RequestBody BookingRequest req) {
        try {
            // 1. Gọi sang field-service kiểm tra sự tồn tại của fieldId
            FieldDto field = fieldClient.get()
                .uri("/api/fields/{id}", req.fieldId())
                .retrieve()
                .onStatus(HttpStatusCode::is4xxClientError, (request, response) -> {
                    throw new FieldNotFoundException("Sân '" + req.fieldId() + "' không tồn tại!");
                })
                .body(FieldDto.class);

            // 2. Nhận 200 OK: Tiếp tục lưu đơn đặt sân vào DB
            Booking saved = new Booking(UUID.randomUUID().toString(), req, field);
            return ResponseEntity.status(HttpStatus.CREATED).body(saved);

        } catch (FieldNotFoundException ex) {
            // 3. Nhận 404: Không tạo lịch, trả về lỗi báo sân không tồn tại
            return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(Map.of("error", ex.getMessage()));
        }
    }
}
REQUEST BODY TỪ CLIENT
public record BookingRequest(

    String fieldId,

    LocalTime startTime,
    LocalTime endTime
) {}
TẠI SAO DÙNG RESTCLIENT TRONG SPRING BOOT 3?
  • Hiện đại & Đồng bộ (Fluent API): Thay thế RestTemplate (đang ở trạng thái bảo trì), cú pháp tương tự WebClient nhưng chạy đồng bộ trực quan.
  • Xử lý Lỗi Tinh gọn (onStatus): Bắt mã lỗi 4xx/5xx ngay trong chuỗi method chaining mà không cần viết các khối try-catch rườm rà.
  • Tự động ánh xạ JSON: Sử dụng HttpMessageConverters để parse JSON trả về trực tiếp thành Java Record FieldDto an toàn kiểu (Type-safe).

booking_service.py (FastAPI + Pydantic + HTTPX)
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel
import httpx, os

app = FastAPI(title="Booking Service (FastAPI)")
FIELD_SERVICE_URL = os.getenv("FIELD_SERVICE_URL", "http://localhost:8081")

class BookingRequest(BaseModel):
    customerId: str
    fieldId: str
    bookingDate: str
    startTime: str
    endTime: str

@app.post("/api/bookings", status_code=status.HTTP_201_CREATED)
async def create_booking(req: BookingRequest):
    # 1. Gọi sang field-service bằng httpx.AsyncClient (Timeout 3s)
    async with httpx.AsyncClient(timeout=3.0) as client:
        try:
            resp = await client.get(f"{FIELD_SERVICE_URL}/api/fields/{req.fieldId}")
        except httpx.ConnectError:
            raise HTTPException(status_code=503, detail="Field Service không phản hồi")

    # 2. Xử lý 404: Không tạo lịch, trả về lỗi sân không tồn tại
    if resp.status_code == 404:
        raise HTTPException(status_code=404, detail=f"Sân '{req.fieldId}' không tồn tại!")

    field = resp.json()
    # 3. Nhận 200 OK: Tiếp tục lưu đơn đặt sân và trả về thành công
    return {
        "bookingId": f"BK-PY-{os.urandom(4).hex().upper()}",
        "customerId": req.customerId, "fieldId": req.fieldId,
        "fieldName": field.get("name"), "status": "CONFIRMED"
    }

Tiêu Chí Đánh Giá Spring Boot 3 (Java 21) FastAPI (Python 3.12)
1. Ngôn Ngữ & Mô Hình Luồng Java: Kiểu dữ liệu tĩnh (Static Typing). Mô hình đa luồng JVM (Multi-threading), hỗ trợ Virtual Threads (Project Loom) xử lý tải lớn. Python: Kiểu động kết hợp Type Hints. Mô hình đơn luồng dựa trên cơ chế AsyncIO Event Loop (uvloop) xử lý non-blocking I/O siêu mượt.
2. Cú Pháp HTTP Client Sử dụng RestClient hoặc WebClient. Cú pháp Fluent API hướng đối tượng, kiểm tra kiểu chặt chẽ (Type-safe), xử lý lỗi qua onStatus(). Sử dụng thư viện httpx.AsyncClient hoặc aiohttp. Cú pháp async / await kết hợp async with cực kỳ tinh gọn, dễ đọc.
3. Cấu Hình & Xử Lý JSON Phụ thuộc vào Jackson ObjectMapper. Cần định nghĩa cấu trúc qua Java Record hoặc POJO Class; ánh xạ qua cơ chế Reflection. Tự động hóa hoàn toàn nhờ Pydantic BaseModel. Tự động kiểm tra dữ liệu đầu vào (Validation) và serialize JSON mà không cần code boilerplate.
4. Thời Gian Khởi Động (Startup Time) Trung bình 1.5 – 4.5 giây (Do quá trình khởi tạo JVM, quét Component Scan, cấu hình IoC Container). Khởi động tức thì: 0.2 – 0.5 giây. Rất lý tưởng cho môi trường Container (Docker), Kubernetes Auto-scaling và Serverless.
5. Mức Độ Phức Tạp & Tiêu Tốn RAM Mức độ phức tạp: Trung bình – Cao. Yêu cầu tuân thủ cấu trúc IoC, DI, Maven. Tiêu thụ RAM trung bình từ 150MB – 350MB. Mức độ phức tạp: Thấp – Trung bình. Cú pháp ngắn gọn, dễ tiếp cận, tích hợp sẵn Swagger UI. Tiêu thụ RAM thấp: 40MB – 80MB.

  • Nếu KHÔNG xử lý ngoại lệ: Lỗi kết nối sẽ văng thẳng ra ngoài luồng, ứng dụng trả về mã lỗi 500 Internal Server Error kèm toàn bộ StackTrace nhạy cảm, gây hoang mang cho người dùng và vi phạm an toàn thông tin.
  • Mục tiêu thiết kế: Bắt gọn ngoại lệ mạng, ghi log cảnh báo và trả về phản hồi lịch sự 503 Service Unavailable.
GlobalExceptionHandler.java (Xử lý tập trung)
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceAccessException.class)
    public ResponseEntity<?> handleNetworkDown(ResourceAccessException ex) {
        // Bắt lỗi kết nối mạng (Connection refused)
        return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
            .body(Map.of(
                "timestamp", Instant.now().toString(),
                "status", 503,
                "error", "Service Unavailable",
                "message", "Hệ thống quản lý sân bãi đang bảo trì. Vui lòng thử lại sau!"
            ));
    }
}

Ý NGHĨA QUAN TRỌNG CỦA TIMEOUT TRONG MICROSERVICES
  • Chống Thắt Cổ Chai (Avoid Thread Starvation): Nếu không có timeout, mỗi request của khách sẽ chiếm giữ 1 worker thread trong 30-60 giây. Chỉ cần 200 khách gọi là toàn bộ server Tomcat cạn kiệt luồng và sập hoàn toàn.
  • Nguyên tắc Fail-Fast: Phát hiện lỗi sớm và ngắt ngay lập tức giúp hệ thống nhanh chóng giải phóng RAM/CPU để phục vụ các yêu cầu khác.

@Service
public class BookingProducer {
    private final RabbitTemplate rabbitTemplate;

    public BookingProducer(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    public void publishBookingCreated(Booking booking) {
        BookingCreatedEvent event = new BookingCreatedEvent(
            booking.getBookingId(),
            booking.getFieldId(),
            booking.getCustomerId(),
            Instant.now()
        );
        // Đẩy sự kiện vào RabbitMQ
        rabbitTemplate.convertAndSend(
            "booking.exchange",
            "booking.created",
            event
        );
        System.out.println("[PRODUCER] Đã bắn sự kiện đặt sân: " + booking.getBookingId());
    }
}

5.2 Thử Thách 2: Cơ Chế Tự Động Thử Lại (Retry) & Fallback
Triển khai Resilience Pattern tự phục hồi trước lỗi mạng chập chờn (Transient Faults)
SLIDE 16 / 18
FieldClientService.java (Tích hợp Spring Retry)
@Service
public class FieldClientService {
    private final RestClient restClient;

    @Retryable(
        retryFor = { ResourceAccessException.class }, // Lỗi mạng tạm thời
        maxAttempts = 3,                              // Thử tối đa 3 lần
        backoff = @Backoff(delay = 1000, multiplier = 1.5) // Giãn cách lũy tiến
    )
    public FieldDto getFieldDetails(String fieldId) {
        System.out.println("Đang kết nối Field Service (lần gọi)...");
        return restClient.get()
            .uri("/api/fields/{id}", fieldId)
            .retrieve()
            .body(FieldDto.class);
    }

    @Recover
    public FieldDto fallbackField(ResourceAccessException ex, String id) {
        System.err.println("Đã thử 3 lần thất bại. Kích hoạt Fallback!");
        throw new ServiceFallbackException(
            "Hệ thống kiểm tra sân bận. Đơn tạm thời chuyển vào hàng chờ duyệt!"
        );
    }
}
CƠ CHẾ HOẠT ĐỘNG CỦA RETRY & BACKOFF
  • Lần 1: Gặp lỗi chập chờn gói tin (Network Glitch). Service không báo lỗi ngay mà dừng 1000ms.
  • Lần 2: Tiếp tục thử lại lần 2. Nếu vẫn lỗi, tăng thời gian chờ lên 1500ms (Multiplier 1.5).
  • Lần 3: Thử lại lần cuối. Nếu Provider đã hồi phục, request hoàn thành mà người dùng không hề biết đã có lỗi xảy ra!
KỊCH BẢN PHỤC HỒI FALLBACK

Khi cả 3 lần thử đều thất bại, hàm @Recover tiếp quản để đưa ra giải pháp thay thế: chuyển giao dịch vào trạng thái PENDING_APPROVAL, hoặc trả về phản hồi fallback thân thiện thay vì làm sập cả hệ thống.

5.3 Đánh Giá Cuối Bài: Giải Đáp Toàn Diện 5 Câu Hỏi Exit Ticket
Tổng hợp các câu hỏi trọng tâm chốt kiến thức môn học kiến trúc Microservices
SLIDE 17 / 18
Câu 1: REST API và Spring Boot có phải là một khái niệm không?
KHÔNG. REST API là một phong cách kiến trúc phần mềm (Architectural Style) định nghĩa các nguyên tắc truyền thông qua giao thức HTTP (stateless, tài nguyên định danh qua URI). Trong khi đó, Spring Boot là một Framework / Nền tảng phát triển ứng dụng Java. Lập trình viên có thể dùng Spring Boot để tạo ra REST API, hoặc tạo ứng dụng console, worker, SOAP web service...
Câu 2: Trong bài toán trên, service nào là Provider, service nào là Consumer?
Field Service là Provider (nhà cung cấp dữ liệu sân bãi qua API GET /api/fields/{id}). Booking Service là Consumer (bên tiêu thụ API của Field Service để xác thực đơn). Trong trường hợp RabbitMQ: Booking Service là Producer (bắn sự kiện), còn Notification Service là Consumer (lắng nghe sự kiện).
Câu 3: Điều gì xảy ra với việc đặt sân nếu field-service ngừng hoạt động?
Việc tạo lịch đặt sân mới sẽ bị gián đoạn ngay lập tức vì Booking Service không thể xác thực sân. Nếu hệ thống có xử lý lỗi & timeout, nó sẽ từ chối đơn một cách an toàn (trả về HTTP 503 hoặc chuyển vào hàng chờ xét duyệt) để tránh tình trạng đặt nhầm sân hư hoặc đặt chồng lấn lịch (Overbooking).
Câu 4: Phân biệt giao tiếp đồng bộ (HTTP) và bất đồng bộ (RabbitMQ)?
Đồng bộ (HTTP/REST): Consumer gửi request và bắt buộc phải chờ Provider phản hồi mới đi tiếp (Chặt chẽ, tốn thread, phụ thuộc thời gian thực).
Bất đồng bộ (RabbitMQ): Producer đẩy thông điệp vào hàng đợi rồi trả kết quả ngay lập tức; Consumer tự lấy xử lý ngầm (Lỏng lẻo, không nghẽn luồng, bền vững).
Câu 5: Khi nào trong bài toán đặt sân nên dùng RabbitMQ thay vì gọi REST trực tiếp?
Nên dùng RabbitMQ cho các tác vụ hậu kỳ (Side-effects / Background Jobs) không cần trả kết quả tức thì cho người dùng: Gửi Email/SMS xác nhận, gửi Push Notification cho chủ sân, tích điểm thưởng khách hàng thân thiết, cập nhật bảng thống kê doanh thu (Analytics), hoặc phát sự kiện realtime qua SSE/Socket (như trong D:\hdvackendpps ealtime).

1. GIAO TIẾP HYBRID

Kết hợp hài hòa giữa REST API Đồng bộ cho các luồng dữ liệu đòi hỏi tính nhất quán tức thì (kiểm tra tồn tại sân, tính tiền) và RabbitMQ Bất đồng bộ cho các tác vụ phụ trợ (gửi thông báo, phân tích).
